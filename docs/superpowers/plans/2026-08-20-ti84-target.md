# TI-84 Plus Target Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build a tiny TI-84 Plus program that runs the `demo/add.rb` mruby bytecode in the mrubyz VM and shows the result (6) on the calculator screen.

**Architecture:** One new C file (`demo/ti84_01.c`) and one new Makefile target. The VM (`mrubyz.c`) already has a non-SMS code path; it needs only one prototype made visible to non-SMS builds. The build uses z88dk's `+ti83p` target (the TI-84 Plus is in the TI-83 Plus family) with `-subtype=asm`, which makes a plain TI-OS `Asm(` program as a `.8xp` file.

**Tech Stack:** z88dk (in the `z88dk/z88dk` Docker image, already used by the Makefile), `mrbc` for bytecode, GNU make, a TI-84 Plus emulator (tilem2) for the run test.

**Spec:** `docs/superpowers/specs/2026-08-20-ti84-target-design.md`

---

## Facts the implementer must know

- The Makefile runs `zcc` in Docker: `ZCC = docker run --platform linux/amd64 --rm -i -v $(PWD):/src z88dk/z88dk zcc`. Paths in the command are relative to the repo root.
- z88dk target name is `+ti83p`, not `+ti8x`. The config file is `lib/config/ti83p.cfg` in z88dk. It lists subtypes: `default` (Ion), `mirage`, `tse`, `asm` (plain TI-OS, `-startup=10`), and `app_one_page` (single-page Flash app, under 16 KB).
- TI-OS refuses `Asm(` programs larger than 8811 bytes. This is the go/no-go gate.
- The console key-wait call is `fgetc_cons()` from `<stdio.h>`. `mallinit()` and `sbrk()` are in `<malloc.h>`.
- `mrubyz.c` line 33 declares `extern uint8_t bytecode_at(uint8_t);` **inside** `#ifdef __SMS__`, but line 1176 calls it unconditionally. Non-SMS builds need that prototype.
- `mrubyz.c` already defines `show_logo`, `restore_font`, `pal1`, `pal2`, and `timer` in its `#ifndef __SMS__` block (lines 54-143). Do NOT define them again in the new file.
- `demo01.c` uses `long _heap; sbrk(&_heap, 4096);`. Do NOT copy that. It claims memory the linker did not reserve.
- A TI-OS program name is up to 8 characters, letters and digits only. So the output file is `build/ti8401` (program `TI8401`), while the make target is `ti84_01`.
- `.gitignore` already ignores `*.bin`, `*.map`, and `*.ruby.c`. It does not ignore `*.8xp`; Task 3 adds that.

### Task 2: Create the test program `demo/ti84_01.c`

**Files:**
- Create: `demo/ti84_01.c`

- [ ] **Step 1: Write the file**

```c
// Tiny mrubyz test program for the TI-84 Plus (z88dk +ti83p, plain TI-OS).
// Runs the demo/add.rb bytecode (a = 2; b = 4; c = a + b) and shows c.
#include <stdio.h>
#include <stdlib.h>
#include <stdint.h>
#include <malloc.h>
#include "mrubyz.h"

// Heap owned by this program. The linker reserves the full array, so the
// allocator cannot hand out memory that belongs to TI-OS.
// Do not copy the `long _heap; sbrk(&_heap, 4096)` trick from demo01.c.
static uint8_t heap[2048];

// The read_bytecode builtin in mrubyz.c calls this. This demo does not use it.
uint8_t bytecode_at(uint8_t i) {
  (void)i;
  return 0;
}

// Defined in demo/add.ruby.c (generated by mrbc from demo/add.rb).
extern const uint8_t bytecode[];

void main() {
  mrbz_val v;
  mrbz_vm vm;

  mallinit();
  sbrk(heap, sizeof(heap));

  printf("mruby on TI-84 Plus\n");
  printf("a=2 b=4 c=a+b\n");

  mrbz_vm_run(&vm, &v, bytecode);

  printf("returned: %d\n", v.u.intval);
  printf("press a key\n");
  fgetc_cons();
}
```

- [ ] **Step 2: Check that it is not an SMS file**

Run: `grep -n 'sms.h\|wait_vblank\|show_logo\|restore_font\|_heap' demo/ti84_01.c`
Expected: no output.

### Task 3: Add the Makefile target and build

**Files:**
- Modify: `Makefile` (after the `demo/add.ruby.c` rule, line 43)
- Modify: `.gitignore`

- [ ] **Step 1: Confirm the target does not exist yet**

Run: `make ti84_01`
Expected: `make: *** No rule to make target 'ti84_01'.  Stop.`

- [ ] **Step 2: Add the target**

Add to `Makefile`, directly after the `demo/add.ruby.c:` rule:

```make
# TI-84 Plus test program (z88dk +ti83p, plain TI-OS `Asm(` executable).
# Output name ti8401 becomes the TI-OS program name TI8401 (8 chars max, letters and digits only).
# Not in DEMOS: `make` builds only the SMS demos; run `make ti84_01` for this one.
TI84_CFLAGS = +ti83p -subtype=asm -vn -m -DAMALLOC

ti84_01: demo/ti84_01.c mrubyz.c demo/add.ruby.c | $(BUILDDIR)
	$(ZCC) $(TI84_CFLAGS) demo/ti84_01.c mrubyz.c demo/add.ruby.c -o $(BUILDDIR)/ti8401 -create-app
```

Also add `ti84_01` to the `.PHONY` line:

```make
.PHONY: all test clean ti84_01
```

- [ ] **Step 3: Build**

Run: `make ti84_01 2>&1 | tail -30`
Expected: the build completes and `build/ti8401.8xp` exists.

If the link reports an **undefined symbol**, the non-SMS path of `mrubyz.c` is missing a stub. Add a stub for that one symbol inside the `#ifndef __SMS__` block of `mrubyz.c`, next to the existing stubs, and rebuild. Do not add anything to `demo/ti84_01.c` except `bytecode_at`.

If the link reports a **duplicate symbol**, `demo/ti84_01.c` defines something `mrubyz.c` already has. Remove it from `demo/ti84_01.c`.

- [ ] **Step 4: Confirm the output is a plain `Asm(` program with the expected name**

Run: `ls -la build/ti8401*` then `xxd -s 0x3c -l 8 build/ti8401.8xp`
Expected: the 8 bytes at offset 0x3C read `TI8401` padded with zero bytes. Then run `xxd -l 96 build/ti8401.8xp` and confirm the program data starts with the two bytes `bb 6d` (the TI-OS "AsmPrgm" token). If the bytes are not there but the header looks sane, do not treat it as a failure — check that `-subtype=asm` is in `TI84_CFLAGS`, note it in the report, and let the emulator run in Task 4 be the real test.

- [ ] **Step 5: Size gate**

Run: `stat -c '%n %s' build/ti8401 build/ti8401.8xp`
Expected: the raw binary `build/ti8401` is **under 8811 bytes**. Record both numbers in the task report.

Then check where BSS and the stack go: `grep -n -i 'bss\|__BSS\|stack' build/ti8401.map | head -20`. Record the BSS start address, BSS size (it must include the 2048-byte `heap`), and the stack address. The program is copied to `0x9D95`. BSS that extends past `0x9D95 + 8811 = 0xC000` would sit on top of TI-OS user variables; if so, report it as a blocker.

**If the raw binary is over 8811 bytes: STOP and report.** Do not continue to Task 4. In the report include: the size, and the result of one retry with size optimization: change `TI84_CFLAGS` to `+ti83p -subtype=asm -vn -m -DAMALLOC -O3 -SO3 --opt-code-size` and rebuild. A known fallback for the user to decide on is z88dk's `-subtype=app_one_page`, which makes a single-page Flash app (limit about 16 KB) instead of an `Asm(` program; it changes the launch method, so it is not a unilateral choice.
